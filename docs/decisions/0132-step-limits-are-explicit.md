# 0132 · 长任务步数上限由显式配置决定

- 状态：accepted
- 日期：2026-11-12
- 范围：[SES-013](../projectneed.md#ses-013-回复循环耗尽后由新输入续额)
- 部分 supersedes：[0129](0129-exhausted-react-budget-renews-on-new-input.md) 的默认 40 次选择；续额协议保留。
- 参考：[上游 #2007](https://github.com/kachofugetsu09/akashic-agent/pull/2007)

## 问题与选择

真实剪贴板修复在准备浏览器验证环境时消耗了 40 次模型输出，任务尚未完成就停止。
回复、调度和子任务各自默认 40，后两者还拒绝 `0`，只关闭回复上限不能覆盖所有执行入口。
用户要求对齐上游优化长任务步数限制，并以独立 PR 交付。

三个入口统一默认 `max_steps = 0`，表示不限总步数；配置正整数时仍使用原 ReAct 上限。
不修改执行循环、失败续额、输出 token 预算、暂时故障重试、工具权限和取消协议。
Wake 的阶段专用预算不属于这三个入口，本次保留。

单纯提高默认数字只会推迟阻断；自动伪造新输入续额会改变来源控制语义；强制委托外部
CLI 又会增加运行环境和权限前提。因此沿用 ReAct 已有的零值语义，由显式配置决定上限。
不设步数上限可能增加调用费用；需要成本边界时应显式配置正数，不把步数当成 token 预算。

## 状态与恢复

只修改源码缺省值和参数校验。配置文件仍由原 owner 管理，不新增迁移、不覆盖已保存的
`max_steps`；显式 `40` 继续生效。Message、模型调用账、ToolCall 和 ToolResult 不改写，
已完成工具不重跑；没有新增数据减少或外部效果权限。

源码回退会恢复旧缺省值。已显式设为 `0` 的调度和子任务配置在旧代码中会校验失败，
回退前须通过正式配置入口改为旧版本支持的正数，不能把配置失败静默降级为 40。
本次 PR 不修改正式配置、不合并、不部署。

## 验证入口

`scripts/react_budget_recovery_workflow.py --entrypoint <reply|scheduler|subagent> --steps 45`
读取相应入口的真实默认配置，使用 loopback HTTP 模型、SourceSession、ReAct、文件工具
和 SQLite 连续完成 45 次文件写入，再提交完成回复；比较既有消息并检查无 UPDATE/DELETE。
同一入口显式传入 `--max-steps 40` 时跑原预算恢复场景，核对触顶、续额、暂停恢复、
插话、账本重开和工具结果保留。所有运行数据只进入临时目录。
